# Work and Project Pages

## Work page purpose

Make all projects discoverable without forcing equal visual weight or requiring images for every entry.

## Work section 1: Introduction and search

- clear statement of the archive's scope
- instant search across title, problem domain, technology, platform, role, and year
- concise result count
- optional command-palette shortcut

**Asset:** one subtle field-map background derived from the Atlas. No large hero illustration.

## Work section 2: Explorer

### Default presentation

A text-first indexed list with title, one-sentence value, year, role, platform, and case-study depth. Rows can reveal approved imagery on hover or focus. Mobile keeps the preview inline or omits it.

### Views

- Index: best for scanning all projects
- Field: spatial relationship view for optional exploration
- Compact grid: only for projects with strong approved imagery

### Filters

- ownership: professional, personal, team
- platform: web, mobile, desktop
- domain: operations, hospitality, education, commerce, tools, experiments
- technology
- year
- depth: case study, story, note

Do not expose every filter at once. Show primary chips and place advanced filters in a drawer.

### Assets

- category glyph set
- project cover where available
- project mark where available
- generated abstract project artwork only when labeled as artwork, never as a screenshot
- one shared empty-media treatment based on project metadata

## Work section 3: Cross-project relationships

Show a compact network of technologies, domains, and roles after the main results, or make it an optional Explorer mode. It should help answer questions such as which projects use Supabase or which systems involved operational workflows.

## Project presentation levels

### Full case study

Use for the strongest, best-documented systems.

1. Identity: title, concise value, year, status, platform, role
2. Context: who or what needed the system
3. System map: users, services, data, and constraints
4. Challenge: one precise problem
5. Decisions: alternatives, trade-offs, and why
6. Product walkthrough: real screens when approved
7. Engineering focus: architecture, correctness, permissions, performance, or platform constraints
8. Contribution: exactly what Kalana owned and what the team owned
9. Outcome: verified result only
10. Reflection: what changed in Kalana's thinking
11. Related work

### Project story

Identity, context, contribution, three key decisions, selected screens or one diagram, technology, and related work.

### Project note

Title, short summary, role, technology, one interesting detail, links, and related projects. No forced long narrative.

## Case-study art direction

Each case study stays inside the Living Emerald family but receives a project-specific green tone and diagram language.

| Project type | Treatment |
| --- | --- |
| Operations and CRM | precise grids, flows, permission maps |
| Kendara | circular chart geometry and Sri Lankan contextual details, handled respectfully |
| Hotel system | operational timelines, ledger and inventory flows |
| POS and commerce | transaction paths, device and inventory relationships |
| Mobile | touch journey, device states, notification or offline flows |
| Experimental | brighter mint, pixel or canvas behavior |

## Required assets per full case study

- Open Graph image, 1200 x 630
- one cover composition, 1600 x 1000 or vector
- three to eight approved screenshots
- one architecture or workflow diagram
- two detail crops
- project mark or category glyph
- optional before-and-after view when factual

## Motion

- metadata locks into place while the cover resolves
- diagrams animate in explanatory order
- screenshot sequences respond to reading progress without scroll hijacking
- sticky side metadata is allowed on desktop and becomes inline on mobile
- related projects inherit a faint connection path from the current project
